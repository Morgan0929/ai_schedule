# 日程创建幂等与租期恢复

## 接口约定

`POST /api/v1/tasks` 必须携带 `Idempotency-Key` 请求头。一次创建及其网络重试复用同一个键，
用户主动发起的新创建使用新键。键允许 1 至 128 位 ASCII 字母、数字与 `-_.:`。
用户身份取自 JWT 和 Redis 会话校验，不由请求体选择。

```http
POST /api/v1/tasks
Authorization: Bearer <token>
Idempotency-Key: 09b2f82f24fc4d048cc1dfe3d2e2c7b1
Content-Type: application/json

{
  "title": "开会",
  "start_time": "2026-10-15T15:00:00",
  "end_time": "2026-10-15T16:00:00"
}
```

| 情况 | HTTP 状态 | 处理 |
| --- | --- | --- |
| 首次创建成功 | 201 | 返回任务，保存首次结果 |
| 同键同内容已成功 | 201 | 返回原结果，`Idempotency-Replayed: true` |
| 同键不同内容 | 409 | 拒绝复用，不创建第二条日程 |
| 原请求仍处理中 | 202 | 返回查询地址、`Retry-After: 1`，不再次执行 |
| 原任务已删除 | 410 | 告知已删除；重新创建需发起新操作并使用新键 |
| 缺少请求头 | 422 | 请求不进入创建流程 |

查询 `GET /api/v1/task-requests/{request_id}` 返回 `PROCESSING`、`SUCCEEDED`、`FAILED` 或 `DELETED`。
查询仅能访问当前用户的记录；不存在或其他用户的记录返回 404。
`can_retry: true` 表示租期已过或发生可恢复失败，客户端可携带原键和原内容再次 POST 竞争恢复，
不是允许直接绕过执行权检查。查询不会自行恢复或重新创建任务。

## 数据与事务

独立表 `request_record` 以 `(user_id, operation, request_id)` 为主键，当前操作为 `tasks.create`。
表中保存规范化请求摘要、原请求内容、状态、持有者随机标识、租期、任务 ID 和首次结果。
它没有指向任务的级联删除外键，也不会自动在 24 小时后清理。
删除任务不删除请求记录，因此旧请求不能复活已删除任务。
任务元数据中的创建标识还用于区分被删除后复用的数据库主键。

领取执行权是一个短事务：插入处理中记录，唯一冲突时检查内容与已有状态。
只有租期已过的处理中记录或服务端失败记录能用原子条件更新接管；同一时刻只有一个新持有者获胜。
业务校验失败（4xx）保存失败结果并原样重放；用户修正内容后应发起新操作，不能改写旧键对应的内容。
服务端失败（5xx）在确认业务事务回滚后标记为可恢复，可用原键重试。
进程直接崩溃或任务取消可能来不及标记失败，保留处理中状态，租期到期后再竞争接管。

执行创建时，先条件更新请求记录，要求状态仍为处理中、持有者匹配且租期有效。
这次更新取得数据库行锁；创建日程、保存成功状态及结果都在同一事务中完成。
提交前再次校验持有者和租期，校验失败则整笔事务回滚，包括已经 flush 的日程 INSERT。
其他接管者需要等待行锁释放，并重新检查条件；旧执行者不能在新持有者接管后提交。

租期默认 30 秒，以数据库时间判断。`renew()` 只能为仍有效且属于自己的执行权续期，不能复活过期租期。
长时间的准备工作可在业务事务外使用 `keep_alive()`，每三分之一租期续期一次；退出上下文会停止心跳。
日程落库本身是短事务，不在数据库行锁内等待用户或模型，也不依赖心跳作为最终正确性保障。
本协议只覆盖同一数据库内的创建，不保证外部邮件、支付等副作用恰好执行一次。

## Agent 与手机端

Agent 的待确认日程用 `pending:<ref_id>` 作为稳定创建键。成功提交后再清理 Redis，
即使 Redis 已被清理或过期，也能从独立请求记录恢复原结果。创建失败时保留 Redis 待确认数据。
确认后改用不同创建内容需要新的操作标识，不能沿用已绑定其他内容的待确认请求。
规则路径和普通创建工具也使用统一创建服务；普通工具可显式传入稳定 `request_id`。
未提供稳定 ID 的新工具调用会分配新键，因此不等于实现了整个 Agent 聊天回合的请求重放。

手机端在创建编辑窗口中生成一次随机键，网络失败或处理中重试复用它，并用本地提交标记减少重复点击。
接口返回 202 时显示处理中提示，不当作创建成功。返回 410 时显示已删除提示；
用户重新打开创建窗口是新操作，会生成新键。
键目前保存在编辑窗口内存中；关闭窗口或重启 App 不会恢复旧的未决创建，不能宣称跨重启重试已有保证。
修改已提交内容、修正确定失败的创建或重新创建被删除日程，应明确开启新的创建窗口。

限流和有界队列仍是独立的资源保护措施，本实现不能代替接口流量控制。

## 部署与验证

启动 `init_db()` 会注册并创建新表。已有 PostgreSQL 也可预先执行
`backend/scripts/migrations/20261014_request_records.sql`。
后端升级要求客户端同步携带请求头；旧客户端创建请求会返回 422。
此处只新增代码和迁移脚本，未迁移远端数据库或部署服务。

```powershell
./venv/Scripts/python.exe -m unittest discover -s backend/tests
```

幂等专项测试支持隔离 SQLite 文件和真实 PostgreSQL 独立 schema，验证并发重试、payload 冲突、用户隔离、删除后重试、
过期接管、旧执行者隔离、事务内插入失败回滚、成功结果重放、续期和 Agent Redis 清理后的恢复。
执行 [PostgreSQL 验证流程](postgres_verification.md) 可验证 PG 时间类型、租期条件更新及事务行为，且不修改线上数据库。
