# 日程与课表的版本号乐观锁

任务表 `task` 与课表 `schedule` 增加 `version INTEGER NOT NULL DEFAULT 1`。
读取和创建接口返回版本号，更新请求必须提交读取时的整数版本号，例如：

```json
{"version": 5, "location": "图书馆"}
```

服务层先验证用户归属与业务参数。最终更新在数据库中同时比较 ID、用户 ID 和版本号，
并递增版本，等价于：

```sql
UPDATE task
SET location = :location, version = version + 1
WHERE id = :id AND user_id = :user_id AND version = :expected_version
RETURNING *;
```

返回一条记录表示本次更新成功；返回零条表示该记录已变化或被删除，更新接口返回 409。
前置查询中的版本比较只是提前发现旧版本，最终的并发保护仍由这条条件更新提供。
来自其他用户的记录在归属检查时返回 404；旧版本不能覆盖新版本。
更新只修改提交的业务字段，`version` 本身只能由数据库递增。

SQLAlchemy 模型也配置了版本列，使任务附件元数据等 ORM 修改不会绕过并发校验。
ORM 发现旧版本时转为业务冲突。删除流程在数据库删除成功后才清理附件文件，
避免并发版本冲突时先删掉仍然有效的文件。

## Agent 与手机端

Agent 更新工具接受 `version`；工作流已有唯一对应的日程查询快照时，将快照版本传入工具。
新指令尚无快照时，工具先读取本人记录并捕获版本，再基于该版本计算和提交修改。
版本冲突不会自动替换成最新版本后重试，也不会回复“已更新”。
这不等于为所有多轮确认流程保留了完整的历史版本快照，复杂确认流程仍应显式传递所选记录的版本。

手机端任务和课程模型保存响应中的版本号，编辑、标记完成和课程更新携带该版本。
收到 409 时刷新列表并显示服务端提示，不自动重放旧修改。编辑窗口中的旧输入不会被自动提交；
用户关闭窗口、查看最新日程后重新编辑。其他 409（例如时间冲突）也会刷新列表，保留原错误提示。

## 已有数据库

启动时 `init_db()` 检查旧表，缺少版本列时添加并将已有记录初始化为 1；重复执行不会重置现有版本。
部署前也可在 PostgreSQL 手动执行：

```text
backend/scripts/migrations/20261008_schedule_versions.sql
```

后端与手机端需要一起更新；旧客户端不携带版本号时，更新接口返回 422。
这里新增的是字段迁移代码与脚本，未执行远端数据库迁移。

## 验证

```powershell
./venv/Scripts/python.exe -m unittest discover -s backend/tests
```

测试包含双设备旧版本提交、正确版本递增、部分字段更新、缺少或伪造版本、Agent 快照冲突、
两个独立事务同时竞争同一版本、旧 ORM 实例写入与旧数据库迁移。
并发数据库测试支持隔离 SQLite 文件，也支持真实 PostgreSQL 的独立随机 schema。
发布前使用 [PostgreSQL 验证流程](postgres_verification.md) 执行真实数据库回归；该流程不修改线上数据库。
